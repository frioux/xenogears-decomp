# Levers: measured C idioms and blockers

Each lever is one measured finding about how this repo's compilers (gcc 2.6.0 / 2.7.2 with cc1 + maspsx) turn C into the retail bytes. Read them through `python3 tools/scripts/lever.py <keyword>...` (AND of keywords over heading, keywords and text; falls back to OR ranked by hits), `--index` for headings with counts and ids, `--symptoms` for the symptom table.

To add a lever: append a block under the heading that matches what the diff shows, in this exact shape, after you have MEASURED it (a closed match or a probe, with the round, unit and function):

    - id: <area>-<short-name> | keywords: three to eight, lowercase, comma separated
      **Lead sentence naming the construct.** What retail shows, the C spelling that produces it, where it was measured.

Headings are ordered by what a worker SEES in a diff. Each heading has a `symptoms:` line (what the diff looks like) and a `try:` line (words to pass to lever.py).

## register choice / allocator tie

symptoms: swapped registers, wrong s-reg, allocator tie
try: regalloc callee-saved swapped tie
- id: a-dead-load-emitted-but | keywords: regalloc, register, callee-saved, cc1, frame, lw
  **A dead load is emitted but only reaches a callee-saved register when its value has a USE** (round 311, cc1_probe replica): cc1 keeps `pVramData = pTarget->pVramData;` with no reader, but puts it in `$v0` and the frame loses 8 bytes. So when retail has `lw $s3,0x24($s0)` and nothing in the function reads it, the original assigned that field to a local that a LATER CALL consumed - look for the argument that used it, not for the load.
- id: a-split-header-rect-out | keywords: regalloc, register, array, cse, hoist, pointer
  **Split a header RECT out of an array of RECTs when one register is doing double duty.** round 312: one `RECT rects[5]` indexed with `rects[count + 1]` makes gcc CSE the array base with a `LoadImage` argument, hoist it above the first call, spill it and rematerialise another argument (796 bytes, 81.88%); `RECT rect; RECT rects[4];` frees exactly the register that keeps the argument in `$s6`. Same family as the two-induction-pointer shape.
- id: a-reusing-existing-local-how | keywords: regalloc, register, callee-saved, gte
  **Reusing an EXISTING local is how you get a value into a callee-saved register** (round 321): a GTE operand like `mtc2 $s1,$8` only appears when the value's live range spans a call, so `rnd = pWork->depthBase + rand() % pWork->depthRange; gte_lddp(rnd)` reusing the `rnd` local puts it in `$s1`, where a separate `depth` local goes to caller-saved `$a0` (battling/misc16 97.73 -> 98.67). Same mechanism as the battle/misc26 packet-code trick: a value retail keeps in a register whose live range does not overlap another's can be expressed by reusing that local.
- id: a-two-similar-blocks-must | keywords: regalloc, register
  **Two similar blocks must not share their locals**: round 326's two threshold blocks see-sawed at 98.38 with one `roll`/`limit` pair and matched at 100.00 once the second block got its own `roll2`/`limit2` - allocation is coupled ACROSS the blocks, so measure the pair rather than one block.
- id: a-two-similar-blocks-must2 | keywords: regalloc, register, permuter, pointer
  **TWO SIMILAR BLOCKS MUST NOT SHARE A POINTER LOCAL - give each arm its own** (round 326 found it, round 335 closed a function with it): `pRow` and `pGearRow` as separate locals cost nothing (disjoint live ranges) and let each block accumulate in place, where one shared local takes a different register per basic block because gcc 2.x has no webs. battle/misc18 func_80098AF8 went 99.84 -> 100.00 on exactly that edit, after 24 declaration orders and a 2235-iteration permuter run had found nothing.
- id: a-shared-callee-saved-register | keywords: regalloc, register, callee-saved, jal
  **A SHARED CALLEE-SAVED REGISTER CAN BE THE BLOCK STRUCTURE, not an allocator tie** (round 335): if retail keeps a constant and a mask in callee-saved registers where your body folds them, check where the call sits. Retail duplicated `MenuSetFt4QuadVertices` in EACH arm and shared only the call AFTER the if/else; with both calls inside the arms gcc hoisted the constants across the first `jal` (92.91), duplicating the call took it to 95.15, and `originY = ...` before `u = ...` in each arm took it to 100.00 (menu/misc6 func_801D36E0).
- id: a-register-allocation-misses-usually | keywords: regalloc, register
  Register allocation misses usually come from local declaration order, split/merged temporaries, or a repeated field load turned into a local (or the reverse).
- id: a-op-redefinition-lever-round | keywords: regalloc, register, cse, move
  THE NO-OP REDEFINITION LEVER (round 155, world_map/misc3 func_800771D8, 99.67 -> 100): when the original does 'move v1,a2' then 'negu v1,v1' and yours folds it to 'negu v1,a2', reassigning the parameter to itself INSIDE the branch ('if (limit < 0) { arg2 = arg2; ... }') stops cse from folding the negate onto the parameter. It looks like debris and is load-bearing; leave a one-line comment.
- id: a-four-shapes-hand-editing | keywords: regalloc, register, cse, delay, loop, move, permuter
  FOUR SHAPES HAND-EDITING DOES NOT MOVE - if the only remaining difference is one of these, do not iterate by hand, run the permuter (RULES) and name the shape in your park note if it finds nothing: CSE_ARG (cse replaces a single-use sum pseudo at the argument position), BLOCK_ROTATION (retail has the loop increment at the TOP of the body block, in a beq delay slot), SCALAR_ADDR (retail keeps a scalar global's ADDRESS in a saved register and loads through it with two different indices; ours folds the address into each load), GIV_TIE (identical instruction multiset, only registers differ).
- id: a-class-instruction-multiset-usually | keywords: regalloc, register, permuter
  THE 95-99.6% CLASS: the instruction multiset is usually already identical and only an allocator tie-break differs (func_801E6578: 20+ hand-written shapes left it untouched; func_800A0C94: 24 declaration orders byte-identical). Hand iteration does not close these, so do not do it: run the permuter (RULES), which tries thousands of such shapes a minute, and prefer a stub with no parked note for your own writing time.
- id: a-hi-register-tie-has | keywords: regalloc, register, cc1, lui, pointer, addiu, hoist, loop
  THE %hi REGISTER TIE HAS A SOURCE ANSWER (round 273, battle/misc27_b func_800B5DF4 99.82 -> 100.00 at retail's exact 456 bytes). cc1 emits a symbol address as TWO pseudos, (set TEMP (high sym)) + (set D (lo_sum TEMP sym)), and the tied form retail shows ('lui s0,%hi' / 'j' / 'addiu s0,s0,%lo') only happens when local_alloc's combine suggestion can pair TEMP with D, which requires D to be a BLOCK-LOCAL quantity. A pointer variable defined in a branch arm and used after the join is cross-block, so it goes to global_alloc and its %hi always lands in $2. So do not hoist the symbol into a pointer local: take the address AT THE USE SITE ('SetRotMatrix(&g_X);' in each arm, letting cross-jumping merge the identical tails), and the %hi ties to the register retail used. This is the same wall as battle/misc35 func_800C0FAC (retail keeps lui %hi(g_BattleWdsEntry) in $s7 across the loop) - try the use-site spelling there too. The way it was found is worth repeating: tools/scripts/cc1_probe.sh <unit> <snippet.c> - a self-contained snippet compiled with the unit's own cc1 and flags in about ten seconds, which prints the assembly and a PROBE <sym> high=<reg> low=<reg> line per address the snippet takes (tools/scripts/probe_example.c is a worked example) answers a register question in minutes that whole-body iteration cannot.

## operand order of addu and arithmetic spelling

symptoms: addu operands swapped, index-first vs base-first
try: addu operand index-first base-first
- id: b-5x-scale-has-two | keywords: addu, operand
  **A 1.5x scale has to be TWO statements**: `stat = stat + (u32)stat * 2;` then `stat = stat >> 1;`. Written as one expression (`stat * 3 / 2`, or `(stat << 1) + stat`) the commutative add comes out in the other operand order and parks at 99.95 at retail's exact size. Do not tidy it back.
- id: b-pointer-local-holding-base | keywords: addu, operand, cast, pointer, u8
  **A pointer local holding the base SEPARATELY from the offset sum is how you get retail's base-vs-index `addu` order.** round 315: `pBase = (u8*)g_Menu->pGearWindowPrims; pEntry = pBase + offset;` emits `addu v1,a0,v1` where every single-expression spelling canonicalises to index-first (99.90 -> 100.00). The converse is equally true and just as useful: a CAST over an index-first sum (`((LINE_F3*)(i * sizeof(LINE_F3) + (u32)base))->f`) is what a fully typed subscript cannot do, because C subscript syntax forces base-first. So the `addu` order is a choice between three spellings, not a wall - measure all three before parking.
- id: b-inline-the-prim-address | keywords: addu, operand, pointer, cast, poly, permuter
  **A named pointer local can COST you the addu order it is supposed to buy - inline the cast into the call arguments when it does.** round 389, menu/misc7_r2 func_801D74EC (gcc 2.6.0): `pPrim = (POLY_FT4*)((u8*)base + primOffset + 0x11D0); ... pPrim->x0` parked at 99.91% with `addu v1,v1,a0` where retail has `addu v1,a0,v1`, and the same sum written inline in the `MenuSetQuadVertices(...)` arguments - repeated seven times, gcc CSEs it - gives retail's order at 100.00%. Adding `pBase`/`pEntry` locals (the b-pointer-local lever that closed round 315 in the same file!) did flip the operand order but also moved g_Menu from `$a0` to `$v1` in both loop preheaders, 97.24%. The permuter found the shape (base=20 best=10, 1391 iters); it does not fix the readability, so report the function ROUGH.
- id: b-accumulator-assignment-keeps-early | keywords: addu, operand, slti, xori
  **An accumulator assignment keeps an early compare in place**: `far |= dz >= 0x800;` leaves the dx compare (`slti`+`xori`) right after the `negu` and before the dz loads, where `farX | farZ` and an inline `(dx >= 0x800) | (dz >= 0x800)` both sink it past the dz compare.
- id: b-redefining-value-already-dead | keywords: addu, operand, addiu, cc1, frame, mult
  **Redefining a value INTO an already-dead local changes how the folder schedules the arithmetic** (round 326): `roll = (flags = rand() % 100 - diff);` (with `flags` dead after its last use) made cc1 place the `addiu` after the remainder and took the body 99.54 -> 99.78, where a separate `limit` local lands it in the divider's post-mult slots and the inline form gets re-associated. A NEW local costs a frame slot; reusing a dead one is free. It also hides the real value behind an unrelated name, so say so in a one-line comment.
- id: b-place-compare-accumulator-emits | keywords: addu, operand, slti, xori
  **An in-place compare accumulator emits retail's `slti`/`xori` shapes**: `dx = dx >= 0x800; ... dz = dz >= 0x800; ... dx |= dz;` writes each compare back into the distance's own register, where `far = dx >= 0x800; far |= dz >= 0x800;` splits every compare through `$v0` and costs instructions (round 328, world_map/misc8). Same family as the `far |= dz >= 0x800;` accumulator lever.
- id: b-shift-has-stay-separate | keywords: addu, operand, sll
  **A shift has to stay a separate operand**: `offset = GetArgument(2);` and then `(offset << 9)` at each use, because writing `offset = GetArgument(2) << 9` lets gcc fold the copy into the `sll` and the body comes out 4 bytes short (round 330, field/misc func_800871B0 97.81 -> 99.59).
- id: b-try-i-vs-i | keywords: addu, operand
  Try `++i` vs `i++` and swapping operands of commutative ops when only instruction order differs.
- id: b-addu-operand-order-follows | keywords: addu, operand, array
  addu operand order follows C order: (i + p->array)->field emits index-first addu, p->array[i].field does not.
- id: b-opposite-side-spelling-lever | keywords: addu, operand, u8, array, cast, lbu, lui, macro
  THE OPPOSITE-SIDE SPELLING LEVER (round 170, battle/misc11 func_800826CC, 84.29 -> 96.00): two references to the same global get SEPARATE 'lui $at / addu $at / lbu %lo(at)' macro forms only when their RTL differs - write one as '*(u8 *)(off + (u32)sym)' and the other as '*(u8 *)((u32)sym + off)', with the index a NAMED local. Inline index expressions, array-vs-cast, volatile and pointer locals all canonicalise into one register and come out 8 bytes short.
- id: b-embedded-assignment-lever-strongest | keywords: addu, operand, u8, cse
  THE EMBEDDED-ASSIGNMENT LEVER (the strongest one for addu operand order): retail emits the BASE-FIRST 'addu d,base,offset' only when that sum is the RESULT OF AN ASSIGNMENT. As a plain sub-expression gcc always canonicalises to offset-first, whatever the C operand order ('(u8*)base + off', 'base[off]', '(u32)base + off', offset-first, bracket forms - all measured identical). So write '*((pSlot = (u8*)base + off) + K) += x' or hand the sum to a local first ('pCounter = base + off; pCounter[K] = 0;'), and keep the embedded locals SEPARATE - reusing one makes gcc CSE them and the address stops being re-derived. It closed menu/misc11_r2's func_801E6B70 from 99.49 after two workers had called the five addu orders uncontrollable.
- id: b-base-statement-lever-round | keywords: addu, operand, addiu, cc1, lui, u16
  THE BASE-IN-A-STATEMENT LEVER (round 149, battle/misc5 func_8007A92C, 84.67 -> 100): when retail materialises a global base with 'lui/addiu' AFTER the loads of the index words instead of above them, declare the base 'mem_addr base;' and ASSIGN it ('base = (mem_addr)D_800D3420;') - a declaration initializer makes cc1 fold the address above the loads. Then write the final address INDEX-FIRST, '((u16 *)((p[1] << 1) + (arg1 * 0x40 + base)))', which gives retail's 'addu' destination and operand order; base-last spellings canonicalise back.
- id: b-element-pointer-local-lever | keywords: addu, operand, lbu, pointer, permuter
  THE ELEMENT-POINTER LOCAL LEVER: a tie of the form retail 'addu v1,v0,v1 / lbu v0,K(v1)' (element address in the BASE) against yours 'addu v0,v0,v1 / lbu v0,K(v0)' (sum coalesced into the scaled INDEX) on a 'table[idx].field' access is closed by giving the ELEMENT a pointer local - 'pElem = &table[idx]; ... pElem->field' - ONE SITE AT A TIME, and it is the opposite of what an old note in this repo claimed. It closed shop_menu's func_801CE480 from 99.71 (four sites; the two accessory loops are coupled, so flipping only one leaves the other tied) after a permuter run from the same body found nothing.
- id: b-global-plus-index-retail | keywords: addu, operand, permuter
  A global plus an index that retail addresses with two chained `addu` (`addu v1,v1,v0` then `addu at,v1,at`): split the base over two statements (`pFlags = D_800C3EA4; pFlags = pFlags + off;`). Any single-expression form gives one `addu` and 99.8% (round 56, battle/misc1 func_80073380, found by the permuter).
- id: b-commutative-sum-will-canonicalise | keywords: addu, operand, cast
  A COMMUTATIVE SUM THAT WILL NOT CANONICALISE (round 126, closed a park round 110 had dated as a wall): when retail has `addu s0,s4,s6` and every spelling gives `addu s0,s6,s4`, do not reorder operands - COPY one parameter into a variable first and sum from the variable: `dy = arg2;` before any other use, then `(s16)(dy + arg4 - 8)` instead of `(s16)(arg2 + arg4 - 8)`. The explicit cast form is required (`dy += arg4 - 8` is 4 bytes bigger and 97.05%), and the copy is what stops gcc folding the two parameters into one commutative pair. The same trick applies wherever a park note blames an addu operand order that survives every source spelling.
- id: b-pdst-base-pdst-i | keywords: addu, operand, u8
  'pDst = base; *(pDst + i + K)' emits a base-first addu where 'p[i + k]' never does; '((u8*)base + i)[K]' keeps the constant offset last.
- id: b-three-statement-shape-levers | keywords: addu, operand, loop, addiu, li, lui, move, nop
  THREE STATEMENT-SHAPE LEVERS FROM ROUNDS 291-292, each measured on a closed match. (a) **Two separate if statements, not if (...) {...} else if (...) {...}**, when retail FALLS THROUGH from the first test's body into the second test: with else if gcc emits j+nop where retail falls through (battle/misc17's BattleRestoreSlotConditionFlags, 448 bytes / 100.00 only in the separate-if form; both forms are semantically identical there because the two conditions are exclusive). (b) **A loop counter's initialiser belongs as its own statement BEFORE the for**, not in the init clause: n1 = 0; then for (i = 0; i < n1; ...). This is the opposite of menu/main/misc3's for (i = 0, matched = 1; ...) lever, where a ONCE-INITIALISED INVARIANT must sit in the init clause to get retail's move a1,zero / li t1,1 order - so: a counter declared before the loop, an invariant inside it. (c) **&g_Array[i] built in TWO statements** (pp = g_Array; pSlot = &pp[i];) emits lui/addiu %hi before the sll where the one-statement form puts it after: 98.80 vs 91.39 (battle/misc23).
- id: b-index-first-subscript-pointer | keywords: addu, operand, pointer, s32
  AN INDEX-FIRST SUBSCRIPT ON A POINTER REPRODUCES RETAIL'S OFFSET-FIRST addu (round 300, menu/misc8_r2): (i * 2 + pCur->renderContexts[i])[g_Menu->pCursors->polysCursor].x0 = ... gives addu v0,v0,a0 where the ordinary polysCursor[...] subscript gives the commuted addu a0,a0,v0 - it fixed eight sites at once (87 -> 90.5 percent on that body). The same trick appears as (s32 *)((u32)((row << 7) + col) * 4 + (u32)g_BattleGridCells) in battling/misc9.
- id: b-do-generalise-winning-spelling | keywords: addu, operand, loop, pointer
  DO NOT GENERALISE A WINNING SPELLING ACROSS SITES IN ONE FUNCTION (round 294). menu/main/misc9's func_801DD5E8: replacing a panel-pointer local with the inline g_Menu->unk430 spelling was worth +5.5 points at both call sites, but re-applying the same edit inside loop 2 regresses 99.58 -> 95.19, and lengthening that local's live range at the other site regresses to 99.34. Each site's register assignment is decided independently; re-measure per site.
- id: b-second-lever-same-class | keywords: addu, operand, delay, jal, s32
  THE SECOND LEVER FOR THE SAME CLASS IS OPERAND ASSOCIATION (round 289): retail often emits '(product + constant) + base' where gcc normalises to '(base + constant) + product'. Only writing the constant against the base - 'p[0x66A] * 40 + (0x320 + (s32)p)' - keeps retail's 'addu a1,a1,v1' in the jal delay slot.

## delay slot

symptoms: nop vs instruction in a delay or load slot
try: delay-slot nop jal slot
- id: c-there-source-ordering-lever | keywords: delay-slot, nop, li, delay, goto, jr, reorg
  **There is no source ordering lever for delay-slot fill** (round 311, ten micro probes): reorg always steals the instruction immediately preceding `jr` in RTL, so a ternary, a comma expression, a goto, an if/else and a scoped block all measure identical. What moves is the RTL position of a `li v0,K` return against trailing constant-zero stores, and with TWO constant-zero stores before `return 1` the `li` is still the one stolen. If a park's only residual is which instruction fills a slot, park it with that number and say so instead of spending the batch.
- id: c-load-load-sub-against | keywords: delay-slot, nop, delay
  **`load/load/sub` against retail's `load/nop/sub` is a DECLARATION-ORDER question, not a scheduling one.** round 370, battling/misc5 func_8007B270 (85.17 -> 100.00): dbr_schedule fills a load-delay slot from a LATER independent insn, so the order in which the channel locals are assigned decides which load gets stolen - the natural ascending `r = p0[0] - 0x80; g = p0[1] - 0x80; b = p0[2] - 0x80;` produced retail's shape where reordering the STORES never moved the tie.
- id: c-original-keeps-li-a0 | keywords: delay-slot, nop, li, delay, jal, move, reorg
  The original keeps `li a0,N` in a `jal`'s delay slot while yours hoists it: gcc has no scheduler here, so the `li` is stolen into the slot by reorg only when it is the last insn before the call and no register conflict blocks it. Move other argument setup earlier, or make the constant argument the last one evaluated.
- id: c-only-difference-hoisted-li | keywords: delay-slot, nop, delay, jal, li
  Only difference is a hoisted `li a0,N` where the original keeps it in the jal delay slot: put the argument in an `int` local before the call, or pass a variable instead of a literal.
- id: c-stolen-delay-slot-retail | keywords: delay-slot, nop, addiu, andi, delay, reorg, sll
  A stolen delay slot (retail has a `nop` where yours has an `andi`/`sll`/`addiu`): the cheapest lever found is the function's RETURN TYPE - `void` lets gcc 2.7.2/2.6.0 reorg steal the instruction into the slot, a non-void type (`int`, `char`, even unused) keeps retail's `nop` (rounds 64-65 closed three functions this way, one of them 99.36% -> 100.00% with no other change). Try that before any statement reordering, and say in a comment why the unused return type is there.
- id: c-make-gcc-put-return | keywords: delay-slot, nop, jr, addu, delay, move
  To make gcc put a return-value copy in the jr $31 delay slot (retail's jr $31 / addu $2,$5,$0 instead of move $2,$5 hoisted to the top), put "$2" in the asm block's clobber list; without it the copy floats above the block (+4 bytes, 98.x%). maspsx also REJECTS hex immediates inside an inline-asm body (invalid literal for int() with base 10: '0x6') - write them decimal, as the matched ScaleMatrix/SetMulMatrix blocks do.
- id: c-two-stores-same-value | keywords: delay-slot, nop, delay, lw, sw
  Two stores of the same value class: SOURCE ORDER decides which one gets the load-delay slot. Retail `lw v0,112(s1); sw v1,4(s2)` (constant store in the delay slot) needs the non-constant store written FIRST (round 47, world_map/misc8 func_80082F64: 98.71 -> 100%).
- id: c-wrong-parameter-type-callee | keywords: delay-slot, nop, addiu, andi, delay, jal, reorg, s32
  A WRONG PARAMETER TYPE ON THE CALLEE COSTS A DELAY SLOT: declaring a callee's first parameter s32 instead of u_char removes an andi a0,a0,0xff at every call site, which is what lets reorg put the following addiu in the jal slot (menu/misc12's func_801E8B4C). Before blaming your caller, check the callee's prototype against its own .s.
- id: c-dead-constant-delay-slot | keywords: delay-slot, nop, delay, cse, reorg
  A DEAD CONSTANT IN A DELAY SLOT CAN BE UNREACHABLE FOR A REASON WORTH RECORDING (round 304): field/dialogue/text_box func_8009C5A8 sits at 99.87 with 469 instructions and ONE differing instruction - retail fills a bne delay slot with a dead ori $s0,zero,0x94 that this build declines to place. cse walks from the flags store into the block after the mode tests (that label has one use), so two assignments of that constant in the arm can never both survive; the extra copy is a reorg fill, not a source shape. When a park is at 99.x with one dead instruction in a delay slot, check whether the two candidate values are the same constant - if so it is this class and no spelling reaches it.
- id: c-s32-return-type-otherwise | keywords: delay-slot, nop, s32, addiu, callee-saved, delay, li, reorg
  AN s32 RETURN TYPE ON AN OTHERWISE VOID FUNCTION can be the last instruction (round 305): with void, reorg steals the branch target's addiu into the final beqz slot where retail has a nop; declaring the function s32 (and not using the value) puts the nop back. Also from the same body: a && with the else arm as the fall-through is what lets gcc delay-slot-fill a li and drop a j where the || spelling costs an extra jump; and a type = 0; STATEMENT after a store beats a declaration initialiser, which keeps the variable live across the first call and costs a callee-saved register.

## extra or missing move

symptoms: one extra or missing move / second copy of a value
try: move copy missing extra
- id: d-repeated-base-i-stride | keywords: move, copy, loop, addu, cc1, delay, permuter, pointer
  **A repeated `base + i * stride` sum that retail COPIES into a second register is source-controllable: give the LOOP its own pointer local.** round 370, battle/misc9 (a permuter find, base 974 -> 263): `pRow = (u16 *)((arg1 & 0xFF) * 0x40 + (s32)g_BattleSlotWordRegs); pRow[idx] = 0; pField = pRow;` and then the loop reads `pField` - the sum pseudo stays live past the copy, so cc1 emits retail's `addu v1,v1,v0` + `move s5,v1` instead of coalescing both uses into `addu s5,v1,a0`. The same body then parked ONE instruction short (93.64%, 344 vs retail's 348) because retail has the `i++` in the beqz delay slot after a call while reorg target-fills the loop test there; that residual is not reachable from source, so park it with the number.
- id: d-live-value-costs-nothing | keywords: move, copy, s32, addiu, addu, li, loop, lw
  **A live-in value that costs nothing is a PARAMETER** (round 335): retail's `lw v0,sym / addu a1,v0,zero / addiu v1,a1,1` copy appears when the local is LIVE AT THE LOAD, and the free spelling is that the value IS one of the function's parameters (the caller already cleared that register). A local initialised to -1 gives the same loop but costs `li a1,-1` (404 vs retail's 400 bytes). system/archive func_8002B8B0 matched at 100.00 as `f(s32 param0, s32 nQueueIndex)`.
- id: d-sltiu-copy-idiom-retail | keywords: move, copy, sltiu, u8, addu, delay, s32
  THE SLTIU-COPY IDIOM: when retail does 'sltiu v0,<x>,1' then 'addu t0,v0,zero' in the 'j' delay slot instead of 'sltiu t0,<x>,1', the boolean local must be u8, not u32/s32 - a u8 return makes gcc compute the compare into v0 and copy it into the return register (two functions first try in battle/misc12 after the u32 versions sat at 95.5%).
- id: d-leftover-a1-a2-jal | keywords: move, copy, delay, jal
  A leftover `$a1`/`$a2` at a `jal` usually means the source passes a COMPUTED value there and the parked C replaced it with a literal: check every call site's delay slot before blaming register allocation (round 47, battling/misc10 func_80084B48: 95.98 -> 100%).
- id: d-two-0xff-immediates-cse | keywords: move, copy, cse, s32

## loop shape and invariant hoisting

- id: g-hoisted-loop-invariant-constant | keywords: loop, hoist, cc1, move, prologue
  **A hoisted loop-invariant constant CAN be stopped from source (round 327; this corrects the round-316 note below).** `loop.c` hoists a constant iff `threshold * savings * m->lifetime >= insn_count`, where `threshold = (loop_has_call ? 1 : 2) * (1 + n_non_fixed_regs)`, `savings` is the number of loads of that value (doubled by `combine_movables` when two loads set the same constant), `lifetime` is the luid span between that value's first and last USE, and `insn_count` is the loop's real-insn count.
