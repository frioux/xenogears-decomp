# Levers: measured C idioms and blockers

Each lever is one measured finding about how this repo's compilers (gcc 2.6.0 / 2.7.2 with cc1 + maspsx) turn C into the retail bytes. Read them through `python3 tools/scripts/lever.py <keyword>...` (AND of keywords over heading, keywords and text; falls back to OR ranked by hits), `--index` for headings with counts and ids, `--symptoms` for the symptom table.

To add a lever: append a block under the heading that matches what the diff shows, in this exact shape, after you have MEASURED it (a closed match or a probe, with the round, unit and function):

    - id: <area>-<short-name> | keywords: three to eight, lowercase, comma separated
      **Lead sentence naming the construct.** What retail shows, the C spelling that produces it, where it was measured.

Headings are ordered by what a worker SEES in a diff. Each heading has a `symptoms:` line (what the diff looks like) and a `try:` line (words to pass to lever.py).

## register choice / allocator tie

symptoms: swapped registers, wrong s-reg, allocator tie
try: regalloc callee-saved swapped tie
- id: a-inline-field-reads-beat-locals | keywords: regalloc, register, local, inline, field, swapped, load, order
  **WHERE TWO FIELD LOADS FEED A DIFFERENCE AND BOTH VALUES ARE ALSO READ IN THE BRANCHY ARMS, DROPPING THE LOCALS AND READING THE FIELDS INLINE LETS cse PICK RETAIL'S REGISTERS AND LOAD ORDER - the locals cost both** (round 397, world_map/main/misc8 func_80085CDC 97.70 -> 99.18, 636 bytes / 158 insns = retail's exact size; residual is one store position, not a register). Retail holds `s16 ang` in `$a1` and `s32 cur` in `$a0` and loads them `lh`-then-`lw`; with locals declared as `s16 ang; s32 cur;` and assigned `ang = pActor->angle; cur = pActor->redStep;` gcc puts ang in `$a0`, cur in `$a1` and emits the `lw` before the `lh` - and swapping the two assignments, making ang `s32`, or the four declaration orders earlier rounds tried all emit that same mirrored body. Writing `d = pActor->angle - pActor->redStep;` with `pActor->redStep + 0x100` / `pActor->angle` in the two slew arms gets both registers and both loads right in one edit, because the pseudos are then created by cse in the order retail's allocator wanted rather than by two named locals. One `do { } while (0)` barrier or a field read-back as a call argument moved nothing (98.93 / identical), and a 3-minute permuter run found nothing (1433 iterations, base 130), so try this spelling before the permuter on any two-local field pair whose only residual is a swap.
- id: a-coalesce-loop-counter-is | keywords: regalloc, counter, iv, memory, loop, frame, permuter
  **AN OUTPUT-COALESCING COUNTER THAT INDEXES THE STORES CANNOT BE MADE MEMORY-RESIDENT FROM SOURCE: `loop.c` turns it into a pointer-iv chain and global-alloc then has a register for it, so retail's per-iteration `sw`/`lw` of the counter is an allocation this C does not express** (round 396, shop_menu/main/misc ShopMenuSellMenu, parked 98.61% at 2024 bytes against retail's 2032 - 2 instructions, the frame and every stack slot identical). Retail at 0xC05C: `addiu t4,t4,1 / sw t4,0x90($fp) / lbu v0,0(a2) / lw t4,0x90($fp)` while the three byte stores still run through the pointer ivs `t0`/`t1`/`t2`, and there is NO store of the initial 0 (the preheader is `addu t4,zero,zero`), so the variable is written by the loop yet its pre-loop value needs no store - which rules out both an ordinary MEM pseudo and a plain register pseudo. Every spelling that makes `itemCount` the counter moves the frame by 8 (itemCount takes `$s7`, pItemSellQtys is spilled): plain 95.95 at 2040 bytes, declaration initialiser 94.65, `u_int` 95.84, `+= 1` 95.95, two counters (`itemType++` and `itemCount++`, which `loop.c` merges back into one giv) 95.95; forcing MEM residency loses the pointer ivs instead (`int itemCount[1]` 90.79, a `*(volatile int *)&itemCount = itemCount + 1` store 91.27, both reloading the counter for each of the three stores), `volatile int itemCount` 90.49, itemType only (no itemCount local, the two while-loop reads using itemType) 95.16 at 2044. Preset ruled out on the same body with try_flags.sh: 2.7.2 -O2 -G8 97.01, 2.7.2-cdk 72.55. Park rather than permute (two earlier runs, 4 and 8 minutes, base 701 -> 666, found a declaration-order no-op and a semantics-changing write).
- id: a-address-taken-pointer-can-never | keywords: regalloc, callee-saved, address-taken, launder, memory, rematerialise, frame
  **AN ADDRESS-TAKEN LOCAL IS A MEMORY VARIABLE TO cc1, so "launder the constant address through a pointer whose address is taken" can hold a base in the frame but can never reach a callee-saved register - that is the wall, not a spelling** (round 396, field/main/misc2 func_8007254C, parked 91.81% at retail's exact 408 bytes). Retail keeps `&g_CamInterpolation` in `$s0` across the `FieldMatrixSetIdentity` jal and reaches `g_CameraEye` etc. as `-0x104($s0)`; the plain pointer form scores 62.01% because a constant pseudo is rematerialised per use, and adding a second pointer taken from the first (`pCamRef = &pCam; *pCamRef`) does give the displacement form (91.81%) but costs a frame slot plus a reload after the call, because gcc never register-allocates an addressable local. `register u_char* pCam` (no launder) is 62.01% again. Screening the LAUNDER body under other presets, which the old note had not done: gcc-2.6.0 -O2 -G0 = 93.88 (the allocator there does keep it), cdk compile-fails, 2.6.0 -O1 = 62.95, -O3 compile-fails - and the unit cannot move to 2.6.0 anyway (five matched neighbours drop to 95.50-99.86). Companion measurement from the same round's other function (func_80072D74): where cse DOES hold a twice-used field address in a register, the STATEMENT POSITION of an unrelated pointer initialiser decides which register it takes and is worth 0.07% - moving `pShake = (s16*)&g_Scene.shakeActive;` from just after the first step to just before the step-square multiplies took 98.99 -> 99.06.
- id: a-symbol-plus-a-big-immediate | keywords: regalloc, register, lui, addiu, li, addu, dg, base
  **A `global + 0x8000` ADDRESS NEEDS `lui/addiu` PLUS `li`/`addu` (an addiu cannot encode +0x8000), and the address pseudo - a `reg/v` USER variable - always takes the LOWER of the two free registers, so a retail body with the constant in `$v0` and the base in `$v1` is only reachable when the base is not a source variable** (round 396, battle/main/misc31 func_800BB9D4, parked 84.11% at retail's exact 228 bytes / 57 insns, whole body one register pair off). `-dg` (regenerate with `docker run --rm -v"$PWD":/w -w /w --platform=linux/amd64 ethos:latest` and the unit's own cc1 + `cc_flags` + `-dg` on `build/src/<unit>.c.i`; the dump lands as `<input>.greg`, and is TRUNCATED for long functions, so read the tail only) shows insn 78/79 `(set (reg/v:SI 2 v0) (lo_sum ...))` for the base and insn 82 `(set (reg:SI 3 v1) (const_int 32768))` for the constant, then local-alloc hands the dead base register to the first load - retail's `lw v1,0xC84(v1)`. Measured: base and the two loads as locals 84.11 (base $v0), both loads inline in the call 83.44 (base $v1 at last, but gcc's right-to-left argument expansion loads 0xC84 before 0xC54 and depth lands in the `jal` slot), primIndex local + depth inline 83.44, `base + 0x8000` as one expression 220 bytes (it folds into the `%lo` addend and the `li`/`addu` disappear - so an exact-size park proves the original spelled the offset as a runtime add). The swap is a local-alloc decision between one 4-ref `reg/v` and one 1-ref scratch; nothing in the source moves it, so park on it.
- id: a-bitfield-store-is-the-same-rtl | keywords: regalloc, bitfield, read-modify-write, mask, tie, word, li
  **A FIELD WRITE THROUGH A BITFIELD COMPILES TO THE SAME `lw/and/ori/sw` RTL as the hand-written mask, so "the original is probably a bitfield store" is never the fix for a $v0/$v1 tie on a flag word** (round 393, slus_006.64/system/temp1 func_80023804, parked 99.10% at retail's exact 312 bytes / 78 insns). A local `union { u32 flags; struct { u32 unk0:7; u32 scale:12; u32 unk13:13; } fields; }` view of SpriteData's flags_0xAC written as `->fields.scale = 0x100` emitted byte-identical instructions to `(flags & 0xFFF8007F) | ((0x100 & 0xFFF) << 7)` (mask in $v1, loaded word in $v0, the reverse of retail), and a 3-minute permuter run (1309 iterations, base 70 best 70) found nothing. The tie itself is worth one diagnostic: in retail the constant mask takes $v0 and the loaded word $v1, and the SAME flip recurs in the unit's func_8002435C (~3 mask $v0 / 0x3C word $v1, 99.19%), so when two functions of one unit flip the same way it is one allocator decision to leave parked, not N ties to chase.
- id: a-base-register-takes-earliest-death | keywords: regalloc, register, base, swapped, death, chain, store, tie
  **TWO IDENTICAL `|=` CHAINS ARE PAIRED TO `$a0`/`$a1` BY RTL DEATH ORDER, NOT BY EMISSION ORDER, so retail whose emitted chain order and register pair disagree was reordered by the post-reload scheduler and cannot be typed** (round 393, battling/main/misc7 func_8007F854, parked 99.17% at retail's exact 96 bytes/24 insns). Four bodies pin the rule - which chain's base pseudo DIES first in RTL (i.e. in source statement order) takes `$a0`, and its value takes `$v0`: plain `A[0] |= K; B[0] |= K;` 96.25 (`$a0`/`$v0` = first chain), the same statements reversed 97.50, `v = A[0] | K; A[0] = v; B[0] |= K;` 98.33, and `A[0] |= K; return B[0] |= K;` 97.92. The return form is the useful find on its own: a RETURNED value is forced into `$2`/`$v0` whatever the statement order, so when retail's LAST chain holds `$v0` and an earlier one holds `$v1` the original returned that chain's value (it reproduced retail's entire order - both `la`, both loads, both oris, both stores, the `lw ra` slot - with only the two BASE registers left swapped, so on a candidates list prefer that body over a permuter body one instruction away). When retail's register pair and its emitted chain order contradict each other, however, source order moves both together and only sched2 could decouple them: `try_flags.sh --sweep` at 97.5 (2.7.2 -O2/-O3 x -G4/-G8; 2.6.0 88.75, cdk 86.5) rules out the preset, and park rather than permute.
- id: a-empty-do-while-block-nudges | keywords: regalloc, block, do-while, addu, operand, tie, permuter
  **AN EMPTY `do { } while (0)` AROUND ONE LOOP BODY MOVES A $v0/$v1 TIE AND COSTS NO INSTRUCTION** (round 392, menu/main/misc9 func_801DD5E8, 99.58 -> 99.72 at retail's exact 424 bytes / 106 insns; `permute.sh` found it in 1403 iterations, base=45 best=30, and its only edit was that block). - id: a-global-allocno-priority-swap | keywords: regalloc, register, swapped, dg, allocno, live, loop
  **`-dg` NAMES WHICH ALLOCNO TAKES `$t0`, AND A VALUE REFERENCED ONLY OUTSIDE A LOOP ALWAYS COMES LAST** (round 392, battle/main/misc11 func_8007FBE0, parked 99.39% at retail's exact 264 bytes/66 insns: retail count=$t0, limit=$t1, color=$t2, the body gives color=$t0, count=$t2). - id: a-global-allocno-priority-is | keywords: regalloc, register, swapped, dg, allocno, priority, size, refs
  **THE `-dg` PROCESSING ORDER IS `floor_log2(n_refs) * n_refs / live_length * size`, SO ONE LOOK AT IT DECIDES WHETHER A SWAPPED CALLEE-SAVED PAIR IS REACHABLE AT ALL** (round 393, menu/main/misc10 func_801E23CC, parked 99.66% at retail's exact 1812 bytes / 453 insns, whole body instruction-identical except that retail keeps the `s32 slot` in `$s2` and the `u8 lastSlot` in `$s1` and ours mirrors them). gcc-2.6.0's `global.c` `allocno_compare` sorts by that quotient (`* 10000 * allocno_size`) and `find_reg` then hands the callee-saved registers out in ascending order along it, so a pair that mirrors is one pair whose two allocnos came out in the wrong order. Two things follow that save a lane: (1) `allocno_size` is the pseudo's MODE SIZE, so a QI (u8) variable carries a 1 where an SI one carries a 4, and the refs term is `floor_log2(refs) * refs` - a variable with 2x the refs of another is ~10x its priority and can never be made to lose the contest by spelling; (2) the divisor is `live_length`, so two values that both start in the loop preheader and span the loop are tied on that term and nothing about declaration order, statement order or declared width moves them. Here the dump (`;; 16 regs to allocate: ... 148 75 72 74 96 73 71 209 91 90`, `75 in 17  72 in 18  74 in 19  96 in 20 ...`, pseudo 75 = slot, 72 = lastSlot) shows the mirror is exactly `slot` processed one slot before `lastSlot`, which the formula makes unavoidable for this body: slot is SI and used 22 times, lastSlot QI and used 11 times, same live length. Retail's reversed order therefore came from a function this C cannot express, not from a missing spelling - stop after one `-dg` look instead of permuting. Measured the same round: `s32 lastSlot` with explicit `(u8)` casts at the loop test and at both calls keeps retail's two `andi` but measures 99.12% / 1804 bytes, and gcc-2.7.2-cdk scores 89.55 on the body (so the preset is not the way out either). Regenerate the dump with `tools/gcc-2.6.0-psx/cc1` and the unit's own `cc_flags` plus `-O2 -G8 -dg` on `build/src/<unit>.c.i`; it writes `<input>.greg`.
- id: a-refs-are-three-times | keywords: regalloc, register, swapped, lreg, refs, insns, local, mask
  **IN `-dl` A BLOCK-LOCAL QTY'S REF COUNT IS THREE TIMES THE NUMBER OF INSN THAT MENTION IT, so "give the loser one more use" means one more INSN, and a body whose two values each appear in 4 and 3 insns can never swap** (round 399, field/main/misc5 func_800A6E70, parked 99.56% at retail's exact 500 bytes / 125 insns, mirrored $v0/$v1 pair only). The dump reads `123 used 12 times across 7 insns` (the mask, 4 insns), `124 used 9 times across 6` (mask+0x10, 3 insns), `122 used 12 times across 22` (j*16), and the block hands out `$3` before `$2` (`72/77/122/123 in 3`, `82/90..100/124 in 2`), so the mask takes `$3` (pri `floor_log2(12)*12*4/7` = 20.6) and mask+0x10 `$2` (18). Retail's pairing (`j*16`/mask in `$2`) needs mask+0x10 to outrank the mask: pri 18 -> 24 requires a fourth insn mentioning it, and retail's stream has exactly one `andi`, one `addiu` from the mask, and two stores each. Useful in both directions: this is how to tell, from the dump alone, whether the flip needs ONE MORE INSN (spell a read-back, a store, a use) or is unreachable. Four permuter runs on that body (base=55 four times) agree.
- id: a-lreg-dump-gives-the | keywords: regalloc, register, swapped, dg, lreg, refs, live, priority
  **THE `-dl`/`-da` LREG DUMP PRINTS THE THREE TERMS OF THE PRIORITY QUOTIENT ITSELF (`Register N used X times across Y insns; ... Z bytes`), so a three-way callee-saved rotation can be PROVEN unreachable in one 10-second compile instead of a session of spellings** (round 396, menu/main/misc1 func_801C6400, parked 98.62% at retail's exact 500 bytes / 125 insns, whole body instruction-identical except that retail keeps pBuffer=`$s0`, i=`$s1`, lineCount=`$s2` and ours rotates them). `-dg` alone gives the order and no numbers, and the numbers are what decide it: i is used 38 times across 70 insns (SI, size 4) -> `floor_log2(38)*38/70*4` = 10.86, lineCount 8 times across 34 (2 bytes) -> 1.41, pBuffer 6 times across 42 -> 1.14, which is exactly the processed order `11 regs to allocate: 119 72 73 142 146 74 71 ...` and hence the `$s0/$s1/$s2` hand-out. Retail's order needs a 6-reference pseudo to outrank a 38-reference one, i.e. 10x, so no C spelling of that body reaches it - the same verdict as `a-global-allocno-priority-is` at a far cheaper price. One extra spelling measured on the way: naming the scanned byte (`u8 c = pBuffer[i];` in place of the two `pBuffer[i]` tests, which cse already merges) leaves the machine code and the whole allocation unchanged at 98.62%, so the "a named temp adds an allocno and reshuffles the sort" hope is dead for this class. Dump recipe: cpp with `-DSKIP_ASM`, then the unit's own `tools/gcc-*-psx/cc1` with its `cc_flags` plus `-O2 -G8 -da`; `m.i.lreg` holds the per-pseudo lines and `m.i.greg` the order and dispositions (allocno numbers there ARE pseudo numbers).

- id: a-in-place-parameter-shift | keywords: regalloc, swapped, shift, parameter, switch, arm, merge, sll
  **A SHIFTED ARGUMENT THAT RETAIL SHIFTS IN PLACE (`sll a2,a2,0x8` as the arm's first instruction) IS A COMPOUND ASSIGNMENT TO THE PARAMETER, NOT `(value << 8)` INSIDE THE STORE: the inline form keeps `value` live into the shared tail, makes a fresh temp, and mirrors the whole register pair** (round 398, field/main/misc11 func_800924D4, 63.71 -> 100.00 at retail's exact 204 bytes / 51 insns, plain Default preset). Retail's four-arm byte setter shifts `$a2` at the head of each arm, holds the mask constant in `$a0` and `index * 4` in `$v1`; `g_FieldWalkmeshMaterialFlags[index] = (g_FieldWalkmeshMaterialFlags[index] & 0xFFFF00FF) | (value << 8);` scored 63.71 with the pair mirrored (mask `$v1`, base `$a0`), the shift emitted late (`sll v1,a2,0x8`) and the arms' tails cross-jumped into a different shared block (228 bytes). Writing `value <<= 8;` as the arm's FIRST statement and `| value` in the store reproduces retail instruction for instruction, after which the constants spell as `~(0xFF << 8)` with no byte change. So when retail shifts an argument into its new position before touching memory, try the in-place shift before blaming the allocator: it is what makes cross-jumping merge the arms the way retail's are merged.

  **A SHORT-LIVED CLAMP TEMP THAT MIRRORS A LONG-LIVED VALUE ACROSS `$v1`/`$a0` IS FLIPPED BY DROPPING THE TEMP TO HImode (`s16`), NOT BY SPLITTING OR REORDERING IT** (round 394, battling/main/misc11 func_80087698, 98.69 -> 100.00 at retail's exact 260 bytes / 65 insns; retail keeps the interpolated per-column value in `$v1` and the table byte it clamps against in `$a0`, mirrored in ours). `-dg` shows why the `s32` body cannot win: `;; 10 regs to allocate: 78 80 81 82 73 72 74 75 76 77` puts the clamp temp (78) ahead of the value (80), and 78 lists hard reg `2` ($v0) among its conflicts (the `slt` results live there), so `find_reg` hands it `$3` and the value `$4` - the priority quotient of the previous lever, with `allocno_size` the only term a spelling can move here (refs 6-vs-9 and the loop's live_length are fixed by the body). - id: a-constant-cse-is-per-mode | keywords: regalloc, cse, constant, mode, li, u8, argument
  **cse's "register holds constant K" knowledge is per MODE, so a narrow-typed competitor is what lets a literal argument keep its own `li`** (round 392, battle/main/misc15 func_8008BED8, parked 99.42% at 1156 vs retail's 1160). - id: a-dead-load-emitted-but | keywords: regalloc, register, callee-saved, cc1, frame, lw

- id: a-ternary-abs-over-a | keywords: regalloc, register, negu, abs, subu, ternary, copy, cse
  **A conditional-expression abs written over a NAMED difference keeps no copy (`negu r,r` in place, then reorg duplicates a following `slt` into the branch slot); spelling the same abs with the subtraction DUPLICATED inside the ternary makes gcc fold the negate into a reversed `subu` instead** (round 392, world_map/main/misc12 func_80090FB4, parked 98.03 at retail's exact 287 insns / 1148 bytes).   **"A LINKER TRICK THAT SHIFTS THE SECTION START" DOES NOT CLOSE A 4-MOD-8 JUMP TABLE, and neither does converting the whole run** (round 391, world_map/misc12 func_80090C68 99.91% / 428 bytes and func_80090E14 99.90% / 416 bytes, both instruction-identical to retail with the `jtbl_` operand as the only residual). check_bin world_map with both converted: `180426` against disc's `180422`, first differing word a `.text` pointer in misc1's rodata (TEXT_START moved +4), and the arithmetic says one alone pays the same pad (the next table then starts 8-aligned) - the unit's rodata (0x800709F8, exactly 0x258 bytes) holds nine tables at +0, +0x18, +0x38, +0x58, +0x15C, +0x18C, +0x1BC, +0x1EC, +0x214, the last five 4 mod 8, and they tile the range with no slack, so the first converted table of that run pays a pad and nothing later shrinks back. Splitting the unit so a new `.rodata` range STARTS at 0x18C does not work either: the `.align 3` raises that object section's `sh_addralign` to 8, so ld pads the section start 0x18C up to 0x190 before the table at object offset 0. - id: i-jtbl-midchain-4mod8 | keywords: jtbl, align, rodata, pad, chain, arithmetic, check_bin
  **AN 8-ALIGNED RANGE END DOES NOT SAVE A CHAIN THAT CONTAINS A 4-MOD-8 TABLE, and a single converted table in an owning unit lands at the START of the object's C `.rodata`, not at its retail offset** (round 396, world_map/main/misc5 func_8007C3B8, parked 98.13% at retail's exact 876 bytes / 219 insns for a scheduler reason of its own). misc5's rodata range is 0x8006FBC4 + 0x1C8 - an 8-ALIGNED SIZE, which is what the align-3 lever's test asks for - and its seven tables tile it at 0x0/0x30/0x50/0x68/0x8C/0x194/0x1AC, the last three 4 mod 8. Apply that test to every table, not to the last one: with all seven emitted from C the offsets become 0x0/0x30/0x50/0x68, then 0x8C pads to 0x90 (0x104 bytes, ends 0x194), the next table pads 0x194 -> 0x198 (+0x18) and the last 0x1B0 (+0x1C) ends 0x1CC - +4 over retail, so TEXT_START moves and check_bin fails (arithmetic from asm/world_map/data/main/misc5.rodata.s, not a check_bin run). Converting ONE stub measures the second half of the rule: misc5's already-matched WorldMapUpdateActorState owns the unit's first C table (0x30 bytes) and C `.rodata` precedes asm `.rodata` in the object, so the asm-owned tables follow it and a newly converted switch's table is emitted at object offset 0x30 - diff_func.sh shows `lw v0,48(at)` where retail has `lw v0,0(at)`. In an owning unit a switch stub is therefore only ever a whole-family change, and the family's FIRST table is what pays the pad.
